# API agent — Gate A contract review v2

## Disposition

The revised proposal addresses the substance of my initial review, and I agree with its direction. In particular, the two-phase attempt anchor/binding is a sensible way to avoid making the receipt self-referential, the `not_due` no-mutation path is preserved, and SBE-local terminal precedence is properly separated from API-parent pre-fence precedence.

**API approves this as the design direction to implement and qualify, with the requirements below.** This is not a claim that the mechanism already works, nor approval of a wheel, release, rollout, profile activation, or paid work. The plan currently requires a matching API handoff and agreement on the executable contract before formally marking Gate A closed; those still need to be recorded, including concrete field/argv and time semantics. I do not recommend holding up bounded implementation research while those details are finalized jointly. If the one-to-one join cannot be demonstrated, use a versioned successor instead of weakening validation.

## Binding and checkpoint ordering

I verified the source-level ordering behind the proposed split. SBE's `checkpoint_basis` derives its members from `snapshot_inventory`, which excludes `native-publication-receipts/`; publication builds a result and workspace snapshot before its receipt. API's `inventory_workspace` enumerates regular workspace files, so an excluded native evidence area can in principle be included in an API archive. Neither observation establishes that the new evidence is actually written before API archives it, remotely durable, or recoverable after restoration: the end-to-end test is essential.

I agree with using the prelaunch envelope's unique `supervision_invocation_id` as the command-attempt key, distinct from the native publication invocation and API job attempt. It is an identifier, not a capability or independent authorization. A closed, versioned binding and a matching typed stdout companion are appropriate. API needs explicit collector/cardinality changes and strict checks against its persisted prelaunch invocation, route, admitted profile, argv, decision and exact result/receipt. Freeze the exact fields, canonical hash rules, and schema versions jointly before relying on them.

**Important qualification:** anchor membership in a snapshot alone does not prove that the publication was produced by that attempt. For example, a later attempt's snapshot could retain anchors from earlier attempts. Require an unambiguous, verifiable publication-to-specific-anchor association under the writer boundary, with native invocation/result/receipt and decision/predecessor relationships checked. The post-seal sidecar's self-hash is not proof of that relationship. Specify what happens if an earlier anchor survives, an incomplete seal is repaired, a publication is replayed, or more than one candidate is present; never select by recency. If the current journal/result format cannot prove the association, extend/version it or choose another demonstrably sound mechanism.

Keep the pre-publication reconciliation snapshot and receipt-retained publication snapshot as separate digest domains; prove the actual ancestry instead of equating their hashes. Prove post-seal evidence does not invalidate native snapshot validation and is included by the real API archive/restore at the required logical root. Inject loss between anchor, seal, receipt, sidecar, stdout and remote checkpoint. Repair only with unique exact evidence and valid authority; otherwise report unresolved. An unpublished local result is not recoverable after losing the only workspace that held it.

The no-publication case should remain explicit in stdout without creating a marker or successor merely for `not_due`. If output is lost, absence of a matching publication is not proof the command was not due.

## Timing and fencing

I agree with actual child request-observation time for request freshness, separate from the fixed cycle decision time; replay must preserve the original observation. Define precise creation/expiry/grace inequalities, UTC format/resolution, injected-clock tests, and clock uncertainty behavior with API before freeze. Preserve compatibility or version any shared observer behavior that changes; old evidence must not be rewritten.

I also agree with the proposed serialized parent observation domain and durable ordering record as the direction for robust precedence, with a process-local monotonic clock only as an aid within that process. The current API implementation persists parent-observed timestamps and compares them strictly; it does **not** yet implement the proposed ordered-event design, so this needs API work and restart/lost-evidence tests rather than being described as an existing guarantee. Distinguish the durable force-fence action from when the parent observes it. A terminal result delivered to the parent after the parent's fence observation cannot gain pre-fence precedence solely from an earlier child seal or request-read time. Missing, equal or contradictory proof remains fenced.

The wave-level description is accurate and appropriately bounded: after admission, up to four GETs may start or finish despite a mid-wave fence; after a valid observed suspension, no next wave. A repeat GET for a proven existing operation may be authorized after recovery, but missing output never authorizes a duplicate paid create. Additional continuation/publication safe points are welcome only if their checkpoint ancestry and writer-held observation are actually proved; otherwise state the narrower guarantee.

## Partial failures and qualification

The expanded failure matrix and distinction between local seal, remote checkpoint, custody ingestion, economics savepoint and outer transaction are correct. Please retain explicit cells for unknown checkpoint acknowledgement, checkpoint-durable/DB-rollback, economics savepoint failure with outer commit, savepoint success with outer rollback, and DB-commit acknowledgement loss. Inspect durable records, exact identities and idempotency after replay; logs and a successful nested savepoint do not prove the outer transaction committed. Missing economics data is not evidence that custody or spend disappeared.

The joined test should use the real installed bounded executable and API collector, strict receiver and actual checkpoint/archive/restore and transaction paths, with synthetic state and controlled fake provider transport. Include the two-attempt/old-anchor case, exact terminal and nonterminal binding, mismatches/tampering, lost-output cases with and without a durable checkpoint, parent-order race, four-GET wave behavior, no duplicate create, and exact-route/shared-observer regression. A provider-free local test is not proof of live Render/storage behavior; later release, rollout and paid canary remain separate decisions.

## Answers to the proposed Gate A questions

1. The current API consumer is **not** ready unchanged: bounded argv is currently mismatched and its collector does not accept the proposed binding companion. API will implement a route-specific closed argv and explicit allowed stream/cardinality/exit mapping, preserving exact and legacy behavior. The exact flags and schemas need a shared fixture rather than an assumed list.
2. Use the versioned attempt-scoped binding and exact reader for both terminal and nonterminal publications, with the one-to-one association and remote-recovery qualifications above. Never recover from generic latest discovery. No-publication remains mutation-free.
3. Use separately recorded cycle time, actual child request observation, and durably established parent ordering. Resolve exact expiry boundaries and clock handling in the handoff; prove checkpoint ancestry and the wave boundary in real-path tests. Ambiguity stays fenced.
4. API owns direct-child exit, lease/fence and custody authority, remote checkpoint persistence, ingestion, reservation and economics semantics. The proposed partial-failure matrix is the right basis; the actual successful durable joins, not child output or logs alone, determine downstream actions.
5. Preserve exact-route regression and compatible worker routing for any existing bound work we actually intend to recover; do not silently substitute versions. The user has said there are no plans to resume the failed 0.4.71 run, but its custody/disposition and any context retirement must be checked independently; that preference alone does not authorize deleting evidence or ignoring exposure. A fresh QA canary follows the joined exact-wheel qualification and separate release/deploy/paid-work approvals.

No code or live state was changed as part of this review.
