# Plan — Frisbee/Hype Prepared-Polish Authority-Request Handoff

## Status

- Slices 0–3 complete: the paired trace and provider-free public inspection prove
  that an intentionally prepared polish action is hidden by an over-broad
  finalization conclusion, and the correction now requires an exact subject-local
  attempt/action/binding join.
- Current gate: reproducible-build and installed-wheel qualification before the
  immutable-tag approval boundary.

## Objective

Determine why identical, fully fanned-in native workspaces prepare a first
ordinary-v2 polish action but expose no external-authority request, then freeze
the narrow public contract needed for API to handle the exact legitimate path.

## Slice 0 — Freeze source topology and paired timeline

- Correlate the two native traces from initial fan-in through review closeout.
- Inventory the preparation, inspection, request projection, and result-publication
  code paths for optional `polish` actions.
- Prove whether the prepared first-polish action is an intentional, admissible
  continuation or work created after a genuinely committed terminal conclusion.
- Distinguish a provisional `FINAL_QA_WARN` awaiting enabled polish from an
  immutable terminal-review conclusion; do not weaken terminal dominance for a
  genuinely committed conclusion.
- Freeze positive and negative controls:
  - enabled, prepared polish must project exactly one ordinary-v2 external-
    authority request; and
  - the same final-QA warning without enabled or pending polish may remain a
    legitimate review closeout.
- Classify what is already established by logs versus what requires a bounded
  checkpoint coordinate packet.
- Pause for reciprocal API review before implementation.

## Slice 1 — Bounded public-evidence decision

- If needed, request one immutable, hash-verified checkpoint HEAD/GET per run,
  no listing or mutation.
- Define the exact request-or-refusal conditions for a prepared polish action.
- Prove that no generic resume/reconciliation can manufacture missing authority.
- Freeze the implementation invariant: terminal dominance remains absolute once
  terminal review is committed, while an SBE-elected and durably prepared polish
  operation makes the preceding final-QA warning provisional until that operation
  reaches a typed disposition.
- Require the same subject's current `SUBMITTED` polish attempt to name the exact
  ledger action, and require that action to be unambiguously pre-provider:
  `PREPARED`, exact `stage=polish` and subject/attempt route, interactive service,
  and no authorization, provider, or consumption evidence. Keep bounded and Batch
  outside this exception.

## Slice 2 — Provider-free public qualification

- Build the smallest installed-wheel fixture that proves the intended
  prepared-polish authority request and the fail-closed requestless case.
- Exercise the production lifecycle boundary and prove that prepared polish is
  represented as ordinary-v2 external authority, never synthetic local work.
- Prove that committed terminal review still prevents all later optional-stage
  selection and authority preparation.
- Audit adjacent optional-stage and custody precedence without broadening the
  exception:
  - `FINAL_QA_FAILED` cannot initiate polish;
  - delivered subjects cannot reopen critic/candidate work;
  - provider-bound polish selects reconciliation;
  - completed polish evidence selects local adoption before terminal closeout;
  - unrelated prepared critic/candidate actions cannot make a warning
    provisional.
- Keep Batch/bounded/qualitative paths out unless code topology proves shared
  behavior.

## Slice 3 — Cross-repo release decision

- Build/install a fresh candidate wheel and run the packaged qualification only
  after the Slice 2 review gate.
- Give API the exact contract, reader/output schema, fixture, and receipt details
  required for its consumer implementation.
- Release only if SBE code/package behavior changes; otherwise explicitly record
  that the correction is API-only.
